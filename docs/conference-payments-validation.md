# 会议收费与公司统一收款

## 使用入口

- 公司收款配置：<http://192.168.2.36:12880/company/payments/>，仅平台管理员。
- 会议收费与订单：`/conference/<会议ID>/payments/`，也可从“办会管理 → 收费与订单”进入。
- 个人付款：“我的参会 → 去付款 / 付款与发票”。原生报名页面的结账入口自动转到同一付款页。

公司管理员先填写真实的公司开户全称、银行支行、账号和财务联系方式，并启用收款。当前没有填写任何真实或演示收款账户，默认关闭。会议管理者不能改收款账户或确认到账。

主办方创建报名表，再到收费与订单保存人民币基础费用。已有人民币报名保留各自的原金额；已有其他币种报名的表单不能直接改成人民币，应新建人民币表单。学生、普通、早鸟票可使用不同报名表，早鸟表设置截止时间；复杂收费选项可在原生字段中配置。收费表要求登录，禁止参会者自行修改金额，信息更正通过主办方处理。应在开放前为各收费表配置人民币价格。

保存费用时必须填写本会议缴费与退款说明，包括基础费用为零但存在收费选项的表单。订单保留当时的说明；参会者勾选同意后才能提交汇款信息或发起在线支付。

流程：报名 → 审核（如启用）→ 待付款订单 → 公司转账/已配置在线通道 → 到账确认 → 报名完成。提交汇款信息只标记待核对；银行流水和金额由公司管理员核对后登记。订单金额由后台计算并固化到快照，金额变化时拒绝继续收款，不静默修改订单。

## 财务处理

财务通过会议订单进入详情，填写实际到账金额和银行流水。重复相同确认幂等，跨订单重复流水拒绝。原生“切换已付款”入口对公司收款会议禁用，避免绕过财务审核。

参会者可申请发票，填写抬头类型、抬头、企业税号及邮箱。财务实际开具并发送发票后登记票号。平台提供可打印付款确认单，明确不属于税务发票；目前未接入电子发票服务商。

退款仅支持全额：参会者申请 → 财务审核 → 在银行/商户后台实际退回 → 登记退款金额、流水及原发票处理说明 → 撤销报名。拒绝申请保留原因，允许重新申请。系统登记退款不会向银行或支付机构自动划款。退款确认相同请求可重试，冲突流水拒绝。公司管理员应先完成资金退回和所需原发票处理。

会议管理者仅可查看/导出本会议财务记录。CSV 防公式注入，支持订单状态筛选、每次最多10000条；页面每页25条。内部操作记录包含时间、操作类型、账号ID，参会者API不暴露内部审核历史。关联订单的报名、报名表和会议禁止直接删除；可撤回会议公开发布并保留账务。公司收费表禁用自动清理，并有永久删除信号保护。遇到旧表启用过自动清理，应先清空该表的保留期限。

## 微信与支付宝配置

`payment-config/merchant.json` 为本机商户配置，默认 `{}`。结构参考同目录 `merchant.example.json`；密钥文件同目录存放，整个目录只读挂载到 Web/Celery。真实配置和密钥均被 `.gitignore` 排除，不通过网页接口返回。请勿将密钥发在聊天或提交到版本库。

微信 Native：公司直连商户号、AppID、商户证书序列号、RSA私钥、APIv3密钥、微信支付公钥ID和对应公钥。当前使用固定配置的微信公钥，不下载或自动信任回调携带的证书。支付宝网页支付：公司应用AppID、seller_id、应用RSA私钥及支付宝公钥，RSA2签名。均不支持服务商分账或个人账户。

在线通道同时要求公司收款启用、完整可读取的RSA密钥、`BASE_URL` 为公网HTTPS且商户配置的 `enabled` 为 `true`。当前内网HTTP部署不启用在线支付。发布公网时须同步调整BASE_URL、Nginx域名/TLS和支付商户后台配置；配置后在公司收款页查看通道状态。

回调地址：`https://<正式域名>/api/payments/notify/wechat`、`https://<正式域名>/api/payments/notify/alipay`。仅此两条回调关闭浏览器CSRF校验，改为RSA验签，微信同时验证时间戳和AES-GCM解密。校验公司商户身份、订单号、金额、币种和订单付款方式，事务提交后才应答。在线成功回调即使重复/并发也只记录一次，浏览器返回页不能确认到账。

原生交易记录统一使用 `_manual` 存储入口，真实支付通道、公司订单和服务商流水写入交易data，品牌工作台显示相应记录；不会伪装成已经安装的第三方Indico插件。支付二维码/收银台地址保留在本订单，禁止同一订单切换通道或混用银行转账。收银台有效期2小时，过期订单、原生管理操作导致金额变化及未能正常入账的通知需联系公司财务核对，不能再次随意付款。当前不自动轮询商户查单、自动关闭/重建过期订单或自动下载服务商账单；可在商户后台核对并按服务商通知重试机制补发通知。

## 存储与验收

PostgreSQL原生 `events.settings`，module=`yujian_payments`，每报名一条JSONB订单；原生 `events.payment_transactions` 保存到账/撤销交易。金额快照、申请和审计持久化，无浏览器本地订单或额外数据库。报名行锁保护同订单并发，银行/退款流水事务锁保护跨订单重复；首次建单还锁报名表和会议以串行处理删除/改费。大量订单时应迁移独立订单表并加索引。

`verify_payments.py` 使用临时管理员、主办方、参会者、会议和报名表；公司开户配置在测试进程内替换，不修改真实收款配置；通知使用内存邮件。验证真实原生收费报名、先审后付、金额边界、越权、CSRF、重复到账、重复流水、发票申请/登记、全额退款撤销报名、删除/永久清理保护、私人CSV及撤回权限。签名测试生成临时RSA密钥，通过真实验签及AES-GCM解密测试微信/支付宝回调，包含并发重试和错误签名、商户、金额、时间戳。

`verify_payments_ui.cjs` 验证公司管理员配置、会议收费/订单、参会付款入口、付款确认单、退款表单、中英切换草稿保留，以及320/390/1440像素布局。浏览器财务写请求全部拦截，银行展示使用明确标记“禁止汇款”的测试响应；实际后台状态变化在隔离内存邮件进程内完成。

真实商户下单/收款、真实退款、税务开票及正式公网回调尚未验证。本轮不修改会议22/61，不自动开启其收费或发布状态。

最终验收：付款业务脚本、320/390/1440界面脚本、原有邮箱账号闭环、原有报名/投稿/审稿闭环、完整会议渲染及内网访问检查均通过。签名回调并发测试只产生一笔交易。两个原有业务测试出现原生 EventPerson SQLAlchemy SAWarning，但断言全部通过。
